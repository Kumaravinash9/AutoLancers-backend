# AutoLancers — backend

Watches Freelancer.com for new postings, scores each one against your profile, and drafts a
tailored proposal for the good ones. Multi-tenant: every table carries a `user_id`, and a posting
is stored once globally while each user's score for it lives separately.

The frontend is a separate repo, `AutoLancers-frontend`. It talks to this over HTTP only — no
shared database, no shared code.

## Quick start

```bash
git clone <this repo> && cd backend
./scripts/bootstrap.sh
uv run python scripts/create_admin.py you@example.com
uv run uvicorn app.main:app --reload --port 8010
```

`bootstrap.sh` checks prerequisites, installs dependencies, starts Postgres, writes a `.env` with
freshly generated encryption and session keys, and applies every migration. It is idempotent —
re-running it never drops data. Use `docker compose down -v` for that.

Then open http://localhost:8010/docs, or start the frontend and go to http://localhost:3000.

### Requirements

| | |
|---|---|
| Python | 3.12+, with [`uv`](https://docs.astral.sh/uv/) |
| Postgres | 16 (a `docker-compose.yml` is included) |
| Docker | running, for that Postgres |
| Gemini API key | https://aistudio.google.com/apikey — free tier is enough to start |
| Freelancer OAuth app | https://accounts.freelancer.com/settings/develop — optional at first |

Discovery works **unauthenticated**, so you can run the poller and see scored jobs before setting
up OAuth at all. A connected account is what adds your own bid history, your outcomes, and your
marketplace profile.

### Why 5434 and 8010

Postgres runs on **5434** and the API on **8010**, not 5432/8000. Both defaults are commonly taken
on a dev machine, and a port collision fails in a way that looks like your own code is broken — an
earlier session here lost real time to an API that turned out to be a different project answering
on 8000. Change them in `.env` if you like; the OAuth redirect URI must then match, both in `.env`
and on the registered Freelancer app.

## Connecting a marketplace account

Two ways, either is fine:

```bash
uv run python scripts/oauth_login.py    # CLI: opens a browser, stores the token
```

or click **Connect** in the frontend, which walks the same authorization-code flow. Tokens are
encrypted at rest with Fernet and refreshed automatically.

You can connect **several Freelancer accounts** to one user. Each keeps its own handle, picture,
rating, skills and bid history, and the account switcher in the navbar scopes the whole app to one
of them or shows them combined. That choice is stored server-side, so it follows you to another
browser.

## Placing bids

This is **not** draft-only any more. `POST /jobs/{id}/bid` submits a real bid to Freelancer, gated
four ways: an explicit confirmation flag in the request, a connected account, a stored token that
actually carries the `bid` scope, and a non-empty proposal body. The scope check runs on the write
path, not only on the availability endpoint the UI reads — a direct POST with a read-only token
must not reach Freelancer, and there is a regression test for exactly that.

Nothing in the polling loop calls it. Bidding always takes a deliberate act.

## Configuration

Everything lives in `.env`; `.env.example` lists every key with a comment. The ones that matter:

| Key | Default | Notes |
|---|---|---|
| `DATABASE_URL` | `…@localhost:5434/automatelancers` | |
| `LLM_PROVIDER` | `gemini` | `gemini` or `anthropic` |
| `GEMINI_API_KEY` | — | required unless using Anthropic |
| `POLL_INTERVAL_SECONDS` | `1800` | 30 minutes |
| `SCHEDULER_ENABLED` | `true` | set `false` to run the API without the poller |
| `TOKEN_ENCRYPTION_KEY` | — | Fernet key; generated by bootstrap |
| `JWT_SECRET` | — | signs session cookies; generated by bootstrap |

## How a cycle works

    poll → normalise → upsert project → score → recommend → draft

`POST /pipeline/run` triggers one by hand, which is the fastest way to check your setup. Nothing in
the cycle may raise past `run_cycle`: one malformed posting, one rate limit or one refused draft
costs that item and nothing else.

Postings are fingerprinted (sha256 over the fields worth reacting to), so re-seeing the same job
every 30 minutes reports `unchanged` rather than a false `updated`.

## Scoring

Two phases. **Hard filters** reject with a stated reason — excluded keywords, a missing required
keyword, or a budget below your floor. Then a **weighted 0–100 score** over skills, budget,
competition and recency, with the weights on the profile so tuning needs no deploy. Every
recommendation stores the reasons it scored what it did.

Competition is **scored, never a gate.** A hard cap on bid count rejected 59 of 75 real postings in
one day — including the only job this profile has won, at 50 bids — because listings here routinely
pass 70 bids within the hour. `crowded_at_bids` is the count that scores half marks, and the decay
is hyperbolic so a 30-bid and a 300-bid job stay distinguishable.

## Drafting

| Provider | Setting | Default model |
|---|---|---|
| Google Gemini (default) | `LLM_PROVIDER=gemini` + `GEMINI_API_KEY` | `gemini-3.6-flash` |
| Anthropic | `LLM_PROVIDER=anthropic` + `ANTHROPIC_API_KEY` | `claude-opus-5` |

The prompt (`app/prompts/proposal_system.md`) is provider-neutral, so switching is a config change.

**Both model families think before answering, and that thinking comes out of the same output budget
as the reply.** On real postings a ~150-word proposal costs ~200 visible tokens but over 1,200
thinking tokens, so `MAX_OUTPUT_TOKENS` is deliberately generous — sizing it for the visible text
alone returns an empty draft. Thinking tokens are counted into stored token usage so cost per bid
isn't understated.

**Free-tier Gemini has per-minute and per-day limits.** A cycle drafts at most
`MAX_DRAFTS_PER_CYCLE` (5), and a rate-limited draft is logged and retried next cycle rather than
lost. Lower `POLL_INTERVAL_SECONDS` cautiously.

## Bid outcomes

`POST /proposals/sync` pulls your real bids back from Freelancer, including ones placed outside
this tool, and maps each award status onto a stored proposal. That is the only source of truth for
whether you won — nothing else in the system can know it.

An unrecognised award status falls back to `SUBMITTED`, never `REJECTED`. Freelancer can add states
at any time, and guessing "rejected" would invent losses and skew every figure built on top.

## Tests

```bash
uv run pytest                      # 67 tests, no database or network needed
uv run ruff check app tests
```

The suite is pure logic — scoring, drafting failure modes, award mapping, identity mapping. There
is no database fixture, so route-level behaviour is verified by hand against a running server.

## Schema changes

`app/db/models.py` is the single source of truth. `docs/target-schema.sql` is a **design
reference — do not run it against a database.** Doing so creates orphan tables Alembic doesn't
track, and collides on `users`.

```bash
# edit app/db/models.py, then
uv run alembic revision --autogenerate -m "what changed"
uv run alembic upgrade head
```

**Read the generated migration before applying it.** Autogenerate cannot know that adding a
`NOT NULL` column to a populated table needs a `server_default`, and will hand you a migration that
fails on any database with rows in it. That has bitten this project four times — it is by far the
most common migration failure here.

## Notes on the Freelancer.com API

- Discovery is `GET /api/projects/0.1/projects/active/`. Polling is the only option — there is no
  public webhook or SSE. The live "Project Alerts" panel on the website runs on an internal,
  session-authenticated socket outside the public API.
- Auth uses Freelancer's own header, `freelancer-oauth-v1`, not `Authorization: Bearer`.
- Most response blocks are opt-in flags. `jobs=true` and `profile_description=true` are what turn
  `/users/0.1/self/` from an id and a username into an actual profile.
- Their terms require cached data to be refreshed at least every 24h. `prune_stale_projects`
  handles it, and keeps anything you drafted or bid on — that is your record, not their cache.
